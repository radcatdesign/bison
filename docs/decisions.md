# Decisions

Two lists. The first is what I decided while building Phase 0 that the brief didn't specify. The second is what I need from you, each with a recommendation.

## Decided while building (tell me if any of these are wrong)
1. **Next.js 16 with Cache Components on.** It's the current default. Every session read sits behind a `<Suspense>` boundary, so the black frame and nav paint first and data streams in. Middleware is now `src/proxy.ts` (Next 16 renamed it).
2. **Kysely and hand-written SQL migrations instead of an ORM.** RLS policies are the most important code in the app, so they live in plain SQL where they're easy to read and review. Kysely gives typed queries without hiding the SQL.
3. **RLS enabled, not forced, with two roles.** Migrations run as the owner role; the app runs as `bisonops_app`, which can't bypass RLS, belongs to no role and owns nothing. Forcing RLS on the owner would break the small lookup functions webhooks need. A test fails the build if the app role ever gains bypass powers or a table ships without the policy.
4. **Roles live in Bison Ops, not in Clerk.** Clerk handles sign-in and organization membership. Owner, Admin, Sales, Marketing and Viewer are stored in `members`. This avoids Clerk custom-role setup per environment and keeps roles working if the auth provider ever changes.
5. **Stand-ins so the whole thing runs without accounts.** A dev sign-in (four made-up people at two made-up companies) replaces Clerk locally and in tests, and is refused on Vercel production. A test billing provider turns items on without Stripe. Real Clerk and Stripe switch on with env vars.
6. **Trials are app-side.** Stripe trials apply to a whole subscription, not one item, so a 14-day trial of one module is an entitlement row with an end date. No card needed. One trial per item per tenant.
7. **Shared contact pages are in Sales and also sold alone.** The brief lists contact sharing under Sales and as an add-on. Both grant the same feature.
8. **Sample data is on for new tenants, generated, never stored.** It's built from a seeded random generator keyed to the tenant, so it's stable and different for every company. Writes refuse while it's on.
9. **Events are partitioned by month.** A daily cron keeps partitions two months ahead and drops data past each tenant's retention (`/api/cron/daily`, scheduled in `vercel.json`).
10. **Webhooks are deduped in the same transaction as the work,** so a failed run can be retried by Stripe without double-processing.
11. **Plain CSS with tokens, no Tailwind.** Brand values are custom properties in `src/app/tokens.css`, so white-label is a token swap. The look is modern and light by default, with a full dark theme that follows the device or a per-person choice (Match my device, Light, Dark) saved in the browser and applied before the page paints. Fonts are Mona Sans (text and numbers, with tabular figures) and Geist Mono (paths and keys), self-hosted from npm. Icons are Lucide.
12. **Last mode is remembered in a cookie set by the browser,** not by the server, so link prefetching can't change it.
13. **Sales and Marketing overviews are real now** (see 35 on for Marketing, 56 on for Sales).
14. **Postgres 16** locally and in tests. Neon runs 16 and 17; nothing here depends on 17.
15. **Domains are unique only once verified.** Anyone can add a domain to their account, but only one account can verify it (DNS check, Phase 1). Nobody can lock a competitor out, and the app never says which domains belong to customers.
16. **New Clerk members wait for approval.** Only invites made in Bison Ops activate on their own. Everyone else is `pending` until an owner or admin approves them (the approve button ships with team management in Phase 1).
17. **Billing and dev sign-in fail closed.** Test billing and the dev sign-in refuse to run on Vercel production, and need an explicit flag in any other production build.
18. **An independent security review** of tenancy, auth and billing ran before this was pushed. Every finding was fixed and has a test.
19. **A public demo mode.** `DEMO_MODE=1` with no `DATABASE_URL` runs the portal with the made-up companies and people, sample data, and every save refused (see 21 for turning modules on). It needs no database, Clerk or Stripe, so a Vercel deploy shows the product in a minute. It refuses to turn on if a database is configured.
20. **Landing page previews load the real page in a sandboxed frame.** It's live and free, and it's what heatmaps will paint over. Some sites block framing; for those, scheduled screenshots (Phase 1) fill in. Sample mode previews made-up sample sites instead of whatever lives at the sample domain.
21. **In the demo, owners can unlock modules and add-ons.** Starting a trial or subscribing works the way it will for real, so people can see a locked mode open up. What they turn on is kept in a cookie in their own browser for 30 days, checked against the catalog and the two demo companies on every request, and never reaches a server. Each visitor starts from the same place, and "Reset the demo plan" on the item's page puts their company back. Everything else in the demo still saves nothing.
22. **Pages live in Marketing.** The landing page maker is part of the Marketing module (feature `marketing.pages`), not the AI Assistant, because a landing page is marketing work and the agent is how you use the tool, not a separate product. Owners, admins and the Marketing role can build and publish.
23. **The agent edits through tools, never by rewriting the page.** Claude gets six tools (add, update, remove and move a section, set the style, set search details), and each call is checked against the page schema and applied as soon as it streams in. The preview fills in while it works, a bad call can't break the page, and every change can be undone.
24. **The agent never invents facts.** No made-up quotes, reviews, prices, dates or numbers. It writes yellow `[Add ...]` placeholders instead, and a page can't be published until they're filled in. Copy follows the Bison Ops rules: plain, no em dashes (stripped if one slips through), no buzzwords.
25. **Claude Sonnet 5.5 by default,** set with `ANTHROPIC_MODEL`. It's fast enough to watch and good at plain copy. The Anthropic SDK is pinned to 0.132.1; the 1.x line shipped a day ago with a breaking API change, so it waits until it's had time in the wild.
26. **An offline helper when Claude isn't connected.** Tests, local work and the demo (until a key is set) use a rules-based stand-in that builds from a brief and follows short, direct changes. It says plainly that it's the offline helper.
27. **Pages ignore sample mode.** They're content a company makes, not data it measures, so they save with sample data on or off.
28. **Published pages live at `/p/<company>/<page>` on the Bison Ops domain for now.** Drafts are never public. The tenant's own domain comes later (see below).
29. **Page forms send to Contacts** as a contact plus a submission marked `landing-page`. A filled hidden field or a send under 1.5 seconds is kept as spam with no contact.
30. **In the demo, pages stay in the visitor's browser,** starting with one finished example page per company. Publishing explains that pages can't go live in the demo.
31. **A second security review of Pages ran after the first push.** Nothing let one company reach another's pages and there was no script injection. It found six smaller issues, all fixed with tests: agent requests now count in their own table when they start, under a per-tenant lock, and can't be erased; published pages go offline when Marketing lapses, and pages can always be taken down; public forms use a server-signed timing token, rate limits, a size cap on read, and never overwrite a known contact's name or phone; the preview frame is sandboxed by header and checks who's talking to it; nothing can be framed by another site; and the demo limiter reads the platform's address header with a daily ceiling.
32. **The Bison logo is the product mark.** One shape, drawn in the current text color so it follows light and dark mode: on a dark tile in the sidebar and app icons, on its own on the sign-in screen. The original files are in `public/brand/`. The old "B" mark and its accent dot are gone.
33. **The page editor's preview runs no scripts.** It first loaded an app page inside a sandboxed frame, which never started on Vercel. Now the editor renders the page into a blank, script-free frame, which is faster and has nothing to break.
34. **Eight page templates, not dozens.** Quote request, product launch, seasonal sale, consultation, event, trade program, free guide and simple contact cover what small businesses build most, each in a different look so the choice is easy. Cards show each template in its own colors; using one applies the company's brand color unless they untick it. Copy works for most businesses as written, and anything only the business knows is a yellow placeholder, the same rule as the agent.

35. **Every Marketing tool has a step-by-step setup.** A Setup page walks a new company through sending, brand kit, subscribers, the welcome series, a first newsletter, the welcome offer and the search pack, in that order (sending first because DNS takes a while). Each tool also shows its own steps at the top until they're done. Steps tick off from what's really saved or verified, never from a checkbox, except one: submitting the sitemap to Google and Bing, which nobody can check for you.
36. **One Resend account for all of Bison Ops, one verified domain per company.** Companies add their own domain from Settings, Email sending, copy the DNS records it shows (with notes for common DNS hosts), and Bison Ops checks every 20 seconds while the page is open. Nobody pastes an API key anywhere. A subdomain like `mail.yourcompany.com` is suggested so marketing email doesn't affect the company's everyday email. Mail only ever goes out From the company's own verified domain.
37. **One table for every email, which is also the queue.** The brief names `newsletter_sends`; it's `email_sends` instead, one row per email to one person for newsletters, series and tests. The send job claims rows with a short lease (so two runs never send the same email), sends up to 100 per Resend batch with an idempotency key, retries failures after 2, 4 and 8 minutes, and drops anything more than 3 days late rather than send it stale. The app can't delete these rows, so the monthly count can't be undone.
38. **The email job runs straight away where it can, and every few minutes when scheduled.** Send now, signups and "start for a list" run it right after responding. Scheduled newsletters and later series emails need `/api/cron/email` every 5 minutes; Vercel's free plan only allows daily cron jobs, so `vercel.json` keeps the daily job (which runs the email job too, as a backstop) and the 5-minute schedule is set up separately (see Needed 21).
39. **Images are stored in Postgres for now.** Every upload is re-encoded with sharp (upright, at most 1,200 px wide, camera details and location stripped) to PNG, JPEG or GIF, the formats every email app shows, up to 2 MB each and 2,000 per company. They're served from `/f/<id>` with a random id, because email apps load images without signing in.
40. **Unsubscribe links carry a signed send id, never an email address.** Every email has one in its footer and in the `List-Unsubscribe` and `List-Unsubscribe-Post` headers, so Gmail and Apple Mail show their own one-click button (RFC 8058). Opening the link never unsubscribes by itself, since link checkers open links; the button does. Unsubscribing keeps working however old the link is, as the law asks; after a year the page just stops offering "Subscribe again".
41. **A do-not-email list, separate from subscribers.** It covers anyone who asked to stop, including form senders who were never on the list. Every send checks it. Unsubscribing stops every series and cancels anything queued. Hard bounces, spam complaints and Resend's own suppressions go on it too; soft bounces don't. The team and imports can't put anyone back; people can by signing up again themselves, and the team can undo an unsubscribe it made.
42. **No open or click tracking.** Apple Mail makes open counts meaningless and it goes against the cookie-free approach. Links to the company's own site get utm tags instead, so visits from email show up in Analytics once the tracking script is in. Results show sent, delivered, bounced and unsubscribed.
43. **Tests go only to people on the team,** so a test can't email anyone else. They count toward the month. Before a domain is verified, tests can come from a Bison Ops address if `EMAIL_FALLBACK_FROM` is set.
44. **Sample mode covers marketing data, not marketing content.** Subscribers, welcome codes and results are sample data while it's on; newsletters, series, the brand kit and settings save either way. Sending to the list is refused while sample data is on, because the list on screen is made up.
45. **The subscriber limit stops imports and adding by hand, never signups.** A real person signing up on a page is always kept.
46. **No double opt-in for now.** The brief doesn't ask for it. People are subscribed when they send a signup form; imports ask the team to confirm everyone agreed. See Needed 23.
47. **"Already in it" means ever.** Nobody gets the same series twice, even after finishing it or unsubscribing and coming back.
48. **One email per day of a series.** Days count from when someone started, so changing or adding emails later moves everyone to the right next email. Off pauses a series without losing anyone's place: turned back on, everyone's schedule moves by however long it was off, so nobody gets several at once. A series can't go on (or stay on) with yellow spots left, or without verified sending and an address.
49. **The welcome code is its own email section.** A ninth section type, "Welcome offer code", shows each new subscriber their own code with what it's worth and when it ends, and disappears for anyone without one. A merge tag would have left a blank for those people. Codes are one per person, ever, and keep the value they were issued with. Sales checks them at checkout, first purchase only, and marks them used when the order is paid.
50. **Series can start from Sales.** "Someone gets an estimate" starts when the team sends one; "Someone leaves a cart" starts when the sales job marks a cart with an email as left behind. Both need Sales and say so when it's off.
51. **Signup forms are landing page forms with "Add to email list" on.** The "I am a..." question is a form field whose choices come from Subscribers, sent as fixed values. The product launch and free guide templates have it on. Forms on the company's own site join in with the tracking script (Phase 1).
52. **The search pack serves files next to the pages it describes.** `sitemap.xml`, `llms.txt` and `llms-full.txt` are at `/p/<company>/`, built live from published pages and the business details. The dashboard's own `robots.txt` lets search engines read `/p/` only, and names each AI crawler for companies that turned AI off. For the company's own site, the search pack gives copy-ready robots.txt lines and a business details snippet. Products from Sales join the sitemap and llms.txt, with a product feed at `/p/<company>/products.xml`. Pre-rendered pages for single-page app sites aren't built; they need the tenant's own domain pointed at Bison Ops first (Needed 16).
53. **Email sending setup lives in Settings,** for owners and admins, because it touches the company's DNS. Everyone with Marketing can see where it stands and send a test once it's done.
54. **Email fonts are limited to ones every device has** (Arial, Helvetica, Georgia and six more). Web fonts don't load in most email apps.
55. **In the demo, Marketing content stays in the visitor's browser,** like pages: brand kit, newsletters, series and settings. Subscribers are sample data. Sending, tests and domain checks are pretend and say so.
56. **Every Sales tool has a step-by-step setup too.** `/sales/setup` walks through payments, products, shipping, checkout, estimates, discount codes and trade accounts, in that order, and each tool shows its own steps until they're done. Steps tick off from what's really connected or saved.
57. **Each company's own Stripe account, through Connect, with no Bison Ops fee.** Accounts are made with Stripe's Accounts v2 API: full Stripe Dashboard, and Stripe collects its fees and covers losses, which is the Standard-account split the brief asked for under Stripe's current API. Payments are direct charges on that account. Bison Ops charges for the module, not a cut of sales (Needed 27).
58. **Checkout is Stripe's, inside the shop's own page.** A Checkout Session in elements mode, not a redirect to a Stripe page, so the cart, live shipping and the order summary sit on one page in the company's colors. Stripe still handles the card, wallets, 3D Secure and receipts. Apple Pay and Google Pay are off for now, because they'd skip the live shipping rate we set from the server (Stripe turns them off in this mode).
59. **The browser only ever holds a cart id.** Every price, trade price, code and limit is worked out on the server each time the cart changes, and changing a cart cancels any checkout already started for it.
60. **An order is recorded from Stripe's own record,** by the webhook or by the thank-you page, whichever comes first. Neither trusts the browser, and a webhook that never arrives can't lose an order.
61. **Codes are Bison Ops', not Stripe promotion codes.** They stay private, can be per account, single use or unlimited, with a total limit, minimum order, dates, one trade account and a team note, and each one is spelled out in a sentence before it's saved. On a checkout they become a one-off coupon for that session. Single-use and per-account codes are held for 60 minutes while someone is checking out, so two people can't spend the same one.
62. **A code that covers the whole order skips Stripe.** The shopper just gives an address and it's a free order, with shipping free too, sent to fulfillment like any other.
63. **Over the order limit, checkout becomes "Ask for a quote."** It lands as a contact, a draft estimate with the cart's lines, and an email to the team.
64. **Shipping is rated live when the company connects a carrier,** ShipStation or UPS, with each product's weight, box and how many fit a box, items that ship alone, and items with their own flat rate. Without a carrier it's a flat or free rate, with an optional handling charge and free shipping over an amount. If live rates fail, checkout says so instead of guessing a price. The ShipStation and UPS adapters follow their current docs and run against stand-ins in tests (Needed 28).
65. **Paid orders go to the team by email and, when it's on, to ShipStation** as an order to pack and label, retried up to 5 times. The order screen shows both, with "send again" for each.
66. **Sales tax is Stripe Tax, off by default.** The company turns it on in Stripe (and adds its registrations there), then in Checkout settings. Tax is added at checkout and on invoices, never in Bison Ops.
67. **Clients approve an estimate by typing their full name.** It's recorded with the time and shown in the history. If the estimate changed while they had it open, they're asked to look again first. A sent estimate can still change (each change is logged); an approved one can't, and Duplicate starts a new one from it.
68. **Invoices are Stripe invoices on the company's account, sent by Bison Ops.** Stripe's own invoice emails are off, so the client gets one email with one Pay link, on their estimate page too. Paying makes an order and tells the team. Marking an estimate paid by hand (check, cash, transfer) voids the open Stripe invoice.
69. **Trade buyers sign in with an emailed link, never a password.** The link opens a page with a Sign in button (so an email app checking the link doesn't sign anyone in), works for 24 hours, and signs them in on that browser for 30 days, for that shop only. Pausing or declining an account signs it out everywhere at once. Their tier comes from 12-month spend (products after discounts and refunds, not shipping or tax) unless the team picks one.
70. **Product pages work with the shop list off,** so a company can share one product without opening a whole shop. They live at `/p/<company>/shop/<product>` for now, like landing pages (Needed 16 covers the company's own domain).
71. **Imports** take a CSV, a Shopify export, a Shopify store's public product list, or a product feed. Importing again updates what came from the same place and keeps the weights, boxes and shipping set in Bison Ops.
72. **Sample mode covers Sales data, not Sales content.** Orders, estimates, carts and trade accounts are made up while it's on, and changing them is refused. Products, codes and settings save either way.
73. **The demo has a shop.** Each made-up company's catalog is browsable, the cart works (it lives in its own id, so nothing is saved), the code WELCOME10 works, and checkout stops with a note where Stripe would take the payment.
74. **A cart counts as left behind** once it has an email and has been quiet for 4 hours (each company can change it). The carts screen shows them first, and the Marketing series can follow up.
75. **Contact sharing makes a read-only page at a link** that lasts 1, 7 or 30 days and can be turned off any time. It shows the person, what they sent, and their orders, estimates and carts, never team notes, and stops if the company loses contact sharing.
76. **Shop pages use plain image tags.** Imported photos keep their original https addresses, which an image optimizer would have to list host by host.
77. **Public Sales endpoints have per-visitor limits** (carts, checkout, shipping rates, quote requests, trade applications and sign-in links, estimate replies), and the ones that email the team have a ceiling per shop, counted per server instance like the form limits (Needed 19).
78. **Order numbers start at 1001 and estimates at 101,** per company, with no gaps from failed payments.
79. **Placeholder Sales limits:** 2,000 products and 500 trade accounts, in `src/config/catalog.ts`.
80. **A security review of Sales ran before release,** separate from the build. Nothing let one company reach another's data, pay into the wrong Stripe account, or record an order without a payment, and there was no script injection. It found two serious gaps, both fixed with tests: an order is now built from what Stripe charged for, line by line, never from the cart (a cart changed during checkout could have shipped more than was paid for), and a code is checked and held under a lock before Stripe is called, with a used row always written for a paid code (a single-use code could have been spent twice). Smaller fixes: the trade form answers the same for every email, quote requests have a timing token and hidden field, the cart endpoint no longer takes an email, rate limits can't be reset with made-up shop addresses, signing in or out of a trade account needs a same-site form post, the payments and shipping stand-ins fail closed outside local work, the stand-in onboarding page only returns to this app, carrier keys are checked by name, a garbled "seen" time counts as stale, and one Stripe account can only belong to one company.
81. **A/B tests run on Bison Ops landing pages only,** not the company's own site or emails yet. A is the live page, copied when the test starts so it holds still; B and C are copies of the live page the team changes in the usual editor. Up to three versions, because each one more splits the visitors thinner.
82. **Visitors are placed without a cookie.** The version comes from a keyed hash of the test, their network address and their browser, so they see the same one every time from the same place, and nothing needs a consent banner. Someone who switches networks may see the other version; that adds a little noise, not bias.
83. **Visitors are counted once a day per test, as a hash keyed with a random salt per company per day.** Salts are deleted after two days, so once a day has passed nobody, us included, can tell who a row was or match it to another day or another test. No address or browser string is stored, and a goal is stored as a yes for that day, not a time, so it can't be lined up with a form send. Visit rows are cleared 30 days after a test ends; each version keeps its totals.
84. **Only people opening the page count.** Not prefetches, prerenders, or the page pulled in as an image or frame by another site; not bots, link previews or scripts (by browser name); not anyone whose browser is signed in to Bison Ops on that domain. One address (an IPv6 block, by its /64) stops counting after 120 visits an hour, and a test after 50,000 visits a day. Everyone still sees a version.
85. **Two goals: a form send, or a click on any button on the page** (the main buttons and the form's send button). A goal only marks a visit already counted that day (or late the night before) for the version that visitor is placed in, so a request from outside can't add visitors or choose which version gets the credit. Click beacons have to come from the page's own site. Spam form sends don't count. Each visitor counts once a day.
86. **Results are Bayesian,** the chance each version's real rate beats A's. A winner is called at 99% (split between B and C when there are both), never before 7 full days and 100 visitors on every version, and only once it has stayed that clear 3 days running (now and at the end of each of the 2 days before). Who's "ahead" is by the rates shown. In simulations of two identical versions checked every few minutes for four weeks, this calls a false winner about 5% of the time (B 2 to 3%), against about 40% for a plain 95% rule checked that often. A B that's 25% better, at 200 visitors a day, is found about 3 times in 4. After 28 days and 1,000 per version with no winner, it says there's no real difference.
87. **The split defaults to even and can't go under 10% per version.** It, the versions and the goal lock once the test starts, so results never mix two setups. The name and notes can still change.
88. **Publishing the page is locked while its test runs,** with a note in the editor, because changing A mid-test would break the comparison. Taking the page offline ends the test, keeping A. Deleting the page deletes its tests. Every version keeps the page's own search details, so search engines see one page whichever version they get.
89. **Ending keeps any version.** Keeping B or C publishes it right away and records it in the page's history. The draft becomes the kept version too, unless it has changes that aren't live yet; those are kept and the editor shows "Live, with changes".
90. **"End on its own" is off by default** and is judged once a day by the daily job, never every few minutes. It only ever keeps a version that's clearly ahead by the rule in 86. A is kept when every other version is clearly worse.
91. **Starting and ending a test, and turning "end on its own" on or off, need the publish role;** setting up needs the edit role. Ending works without the plan, so a lapsed trial can always stop a test.
92. **Sample mode covers results, not tests.** Tests and versions save either way; with sample data on, the results are made up and say so. The demo shows two made-up tests and changes nothing.
93. **Placeholder limit: 5 tests running at once** with Marketing, in `src/config/catalog.ts`.
94. **A security review of A/B tests ran before release,** separate from the build. Nothing let one company reach another's tests or pages. It found that a script could forge conversions for the version of its choice, and that checking results every few minutes made a 95% bar far too easy to cross by luck; both are fixed with tests (goals only mark a visit already counted for the visitor's own version, and the winner rule in 86). Smaller fixes: page opens only, IPv6 limits by block, a per-test ceiling, salts that are deleted (the first version's hash could be recomputed by anyone with the app's secret), the test id in the hash, no timestamps on goals, a winner when A had none, page-first locking so publishing, starting and ending can't race, B locked while the test starts, placeholders checked again before a kept version goes live, late visits kept off ended tests, and cleanup for suspended companies too.
95. **Fit Funnels is an edition, not a fork.** One app, one database, one set of tools and tests. A company is in one edition, set at signup and not changeable from the app (only the schema owner can). Without an explicit edition, the kind of business decides: gym and studio are Fit Funnels.
96. **Before sign-in, the edition comes from `?edition=fit`, then the host name (`FIT_FUNNELS_HOSTS`), then Bison Ops.** The dev and demo sign-in has a two-way switch; real sign-in shows the edition of the address it's opened on, and every signed-in screen follows the company's own edition.
97. **Fit Funnels' look:** an F of three bars, shorter as they go down, each ending in a curve (from the artwork in `public/brand/fit-logo.svg`), on the same dark tile as the bison; a default accent of `#f76b15` (orange, distinct from the error red); its own tab titles, app icon and install manifest. Its second chart color is blue so it doesn't sit next to the orange accent.
98. **Fit Funnels' names** for the same tools: Leads, Funnel pages, Intro offer, Membership sales, Quotes, Purchases, Memberships, Promo codes, Corporate accounts and Unfinished joins, plus the add-ons Membership calculator, Plan builder, Member library and Club gallery. Mode names (Analyze, Marketing, Sales) stay, since they read right for a club too.
99. **Words are written in place, both versions side by side** (`say("Bison Ops words", "Fit Funnels words")`), not looked up by key, so every sentence reads naturally and the Bison Ops text can't drift. Names used in many places (nav, modules) live in the edition config.
100. **Made-up clubs:** Summit Strength Club, a full gym (sample data on, Marketing included, like Brightwater) and Pulse Cycle Studio, a boutique cycling studio (sample data off, no modules, like Ridgeline). People: Maya Reyes (owner) and Theo Banks (sales) at Summit, Jo Whitaker (owner) and Sam Okoro (marketing) at Pulse.
101. **Prices and limits are the same in both editions** for now (placeholders in the catalog).
102. **Accent-derived colors now follow the company's accent.** Soft fills, outlines, text and focus rings were computed from the default accent at the root, so a recolored company kept blue highlights. They're recomputed wherever the accent is set. Bison Ops companies on the default accent see no change.
103. **The nav groups pages into categories.** Overview and Setup stay at the top; the rest sit in categories that open in place to show their pages (Marketing: Email, Pages and tests, Brand and search; Sales: Selling, Catalog and checkout). Analyze has too few pages to need them. A closed category shows how many pages it holds. Which ones are open is remembered per browser, and the one holding the current page is always open. Categories are named per edition, so a club sees "Funnels and tests" and "Memberships and checkout". Groups live on each page in `src/config/modes.ts`.
